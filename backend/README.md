# ServeEasy backend

FastAPI + SQLAlchemy 2 + Alembic on Neon Postgres. Python deps are managed with [uv](https://docs.astral.sh/uv/).

## Setup

Requires `uv` (it installs Python 3.13 for you).

```bash
cd backend
uv sync
```

### Database connection

The app needs two Neon connection strings in `backend/.env` (git-ignored):

| Variable | Used by | Why |
| --- | --- | --- |
| `DATABASE_URL` | the API at runtime | pooled (`-pooler` host), good for many short connections |
| `DATABASE_URL_UNPOOLED` | migrations and the seed script | direct, because pooling can break session-level operations |

Get them from the Neon CLI (project `serve`):

```bash
neon env pull --project-id shy-leaf-28982656 --branch production --file .env \
  -e DATABASE_URL,DATABASE_URL_UNPOOLED
```

Or copy `.env.example` to `.env` and fill them in by hand. Never commit `.env`.

## Everyday commands

```bash
uv run alembic upgrade head           # create or update the schema
uv run python -m app.seed             # load the demo UTM data (safe to re-run)
uv run uvicorn app.main:app --reload  # run the API on http://localhost:8000
uv run pytest                         # run the tests
```

Interactive API docs are at http://localhost:8000/docs.

## Migrations

Alembic manages only the `public` schema. Neon Auth's `neon_auth` schema is not touched.

```bash
uv run alembic revision --autogenerate -m "describe the change"   # then review the file
uv run alembic upgrade head
uv run alembic check                                              # models and DB in sync?
```

Always read an autogenerated migration before applying it.

## Seed data

`app/seed/data.py` holds the demo data: 15 users, 25 listings, 4 cafeterias with menus,
7 services, plus orders, bookings and chat messages. Place names are real UTM places;
all people, businesses, emails, phones and payment references are fictional.

The seed is idempotent. Every row has a stable id, and the runner upserts by id, so running it
twice gives the same database as running it once.

```bash
uv run python -m app.seed                 # insert or refresh seeded rows
uv run python -m app.seed --reset --yes   # DESTRUCTIVE: empty the app tables, then reseed
```

Notes:

- An upsert overwrites hand edits to seeded rows. Rows you add yourself are left alone.
- Removing a row from `data.py` does not delete it from the database; use `--reset`.
- `--reset` touches only the 8 app tables, never `neon_auth` or `alembic_version`.
- The tests call the same seed code, so they need Neon access too.

## API (read-only for now)

| Endpoint | Description |
| --- | --- |
| `GET /health` | checks the database connection |
| `GET /listings` | active listings; filters `category`, `condition`, `min_price`, `max_price`, `q` (title search); `limit`, `offset` |
| `GET /cafeterias` | food sellers |
| `GET /cafeterias/{id}/menu` | available menu items; optional `meal_session=lunch\|dinner` |
| `GET /services` | service listings; optional `category`; `limit`, `offset` |

Money is returned as a decimal string (for example `"8.50"`), not a float.
Responses only expose a seller's `id`, `name` and `image`; email, phone and student id stay private.

## Authentication (not implemented yet)

There is no login and no write endpoints. The `users` table has no password column and uses string
ids with Better Auth-style field names, so auth can be added later. The open decision is whether to
use Neon Auth (managed Better Auth, already provisioned in the `neon_auth` schema) or self-hosted
Better Auth in the frontend. Writes (creating listings, orders, bookings, chat) should wait for that.

## Layout

```
app/
  config.py      settings and URL helpers
  db.py          engine and session dependency
  main.py        FastAPI app
  models/        SQLAlchemy models
  routers/       listings, cafeterias, services
  schemas.py     Pydantic response models
  seed/          data.py (the data), runner.py (upserts), __main__.py (CLI)
alembic/         migrations
tests/
```
