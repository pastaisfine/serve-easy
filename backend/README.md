# ServeEasy backend

FastAPI + SQLAlchemy 2 + Alembic on Neon Postgres. Python deps are managed with [uv](https://docs.astral.sh/uv/).

## Setup

Requires `uv` (it installs Python 3.13 for you).

```bash
cd backend
uv sync
```

### Database connection

The app needs two Neon connection strings in `backend/.env` (git-ignored):

| Variable | Used by | Why |
| --- | --- | --- |
| `DATABASE_URL` | the API at runtime | pooled (`-pooler` host), good for many short connections |
| `DATABASE_URL_UNPOOLED` | migrations and the seed script | direct, because pooling can break session-level operations |

Get them from the Neon CLI (project `serve`):

```bash
neon env pull --project-id shy-leaf-28982656 --branch production --file .env \
  -e DATABASE_URL,DATABASE_URL_UNPOOLED
```

Or copy `.env.example` to `.env` and fill them in by hand. Never commit `.env`.

## Everyday commands

```bash
uv run alembic upgrade head           # create or update the schema
uv run python -m app.seed             # load the demo UTM data (safe to re-run)
uv run uvicorn app.main:app --reload  # run the API on http://localhost:8000
uv run pytest                         # run the tests
```

Interactive API docs are at http://localhost:8000/docs.

## Migrations

Alembic manages only the `public` schema. Neon Auth's `neon_auth` schema is not touched.

```bash
uv run alembic revision --autogenerate -m "describe the change"   # then review the file
uv run alembic upgrade head
uv run alembic check                                              # models and DB in sync?
```

Always read an autogenerated migration before applying it.

## Seed data

`app/seed/data.py` holds the demo data: 55 users, 3 shops, 214 listings, 4 cafeterias with menus,
209 services, plus orders, bookings and notifications. Place names are real UTM places, and
**The Cube** (a student-run shaved ice and dessert shop) uses real details supplied by the project
owner. Its owner account, the other two shops, all other people, businesses, emails, phones and
payment references are fictional. Listing and service photos are Unsplash images the frontend
already allows (some are loose matches); shop logos, avatars and menu items still use text placeholders.

Categories live in `app/models/base.py` (Postgres enums) and the frontend's `lib/categories.ts`.
Keep both in sync. Migration `0003` removed `furniture` from listings and added the
snacks, daily_essentials, hobbies, tickets, design, media, programming, errands and rentals categories.
Postgres cannot drop an enum value, so removing one means recreating the type (see 0003).

The seed is idempotent. Every row has a stable id, and the runner upserts by id, so running it
twice gives the same database as running it once.

```bash
uv run python -m app.seed                 # insert or refresh seeded rows
uv run python -m app.seed --reset --yes   # DESTRUCTIVE: empty the app tables, then reseed
```

Notes:

- An upsert overwrites hand edits to seeded rows. Rows you add yourself are left alone.
- Removing a row from `data.py` does not delete it from the database; use `--reset`.
- `--reset` touches only the application tables listed in `app/seed/data.py`, never `neon_auth` or
  `alembic_version`. Empty workflow tables are listed there so reset clears related request data too.
- The tests call the same seed code, so they need Neon access too.

## API

| Endpoint | Description |
| --- | --- |
| `GET /health` | checks the database connection |
| `GET /listings` | active listings, newest first; filters `category`, `condition`, `min_price`, `max_price`, `q` (title search); `limit`, `offset`. Each has a free-text `spot` and an optional `shop` link |
| `POST /product-orders` | student requests to buy an active listing; stores the price and meetup spot snapshot and reserves the listing |
| `GET /product-orders/mine` | the signed-in student's purchase requests and the seller's incoming requests |
| `GET /product-orders/{id}` | one purchase request for its buyer or seller |
| `PATCH /product-orders/{id}` | seller accepts/declines or completes; buyer cancels a pending/accepted request |
| `GET /notifications/mine` | the signed-in user's newest in-app notifications |
| `GET /notifications/unread-count` | the signed-in user's unread notification count |
| `PATCH /notifications/{id}/read` | mark one of the signed-in user's notifications as read |
| `POST /notifications/read-all` | mark all of the signed-in user's notifications as read |
| `PATCH /me/contact` | update the signed-in user's public WhatsApp and Telegram contacts |
| `GET /cafeterias` | food sellers |
| `GET /cafeterias/{id}/menu` | available menu items; optional `meal_session=lunch\|dinner` |
| `PATCH /meals/provider/contact` | update the signed-in food staff member's cafeteria contacts |
| `GET /services` | services, newest first; optional `category` (`printing`, `tailoring`, `repair`, `grooming`, `tutoring`, `other`); `limit`, `offset`. Each has `spot`, optional `unit` and `image`, and an optional `shop` link |
| `POST /service-bookings` | student requests a service for a date with details; starts in `pending` |
| `GET /service-bookings/mine` | the student's bookings and provider's incoming bookings |
| `GET /service-bookings/{id}` | one booking for its student or service provider |
| `PATCH /service-bookings/{id}` | provider accepts/declines or completes; student cancels a pending/accepted booking |
| `GET /shops` | student enterprise profiles (informational only, no ordering) |
| `GET /shops/{id}` | a shop's info (name, description, logo, location, hours, owner) plus the listings and services that belong to it |

Money is returned as a decimal string (for example `"8.50"`), not a float.
Public item and service responses include optional WhatsApp and Telegram contact links alongside seller identity; email and student ID stay private. Cafeteria contacts are public on menu responses. The Telegram bot intentionally omits contact links from its rendered replies.
All order and booking mutations require a verified Neon Auth session. Item requests move through
`pending`, `accepted`, `declined`, `completed`, or `cancelled`; only one pending/accepted request
can reserve a listing at a time. Completing a request marks the listing sold; declining or cancelling
releases it. These marketplace requests do not collect payment.

Product-order events create persistent in-app notifications for the relevant buyer or seller in the
same database transaction as the order change. This currently covers request submission, acceptance,
decline, cancellation, and completion; email delivery is not configured.

Item categories: `books`, `electronics`, `clothing`, `kitchen`, `stationery`, `sports`, `snacks`,
`daily_essentials`, `hobbies`, `tickets`, `other`.

## Telegram bot

The bot answers marketplace questions straight from Telegram. It reads the same Neon database as
the API and never writes: it runs on its own engine where every transaction is opened with
`SET TRANSACTION READ ONLY`, so Postgres itself refuses any write from the bot.

Set the token in `.env` and the bot starts with the API:

```bash
TELEGRAM_BOT_TOKEN=123456:ABC...
uv run uvicorn app.main:app --reload
```

Without a token nothing happens; the API starts as before.

| Command | What it does |
| --- | --- |
| `/listings [text]` | items for sale, newest first; buttons filter by category and price |
| `/services [text]` | services, newest first; same filters |
| `/search <text>` | items and services at once |
| `/cafeterias` | the food sellers |
| `/menu <name>` | a cafeteria's lunch and dinner menu with prices |
| `/shops` | the student enterprises |
| `/shop <name>` | a shop with the items and services it offers |

Typing plain text searches items and services. Every reply shows five results per page with
buttons for the next page, the categories and the price.

The bot reuses the API's response schemas, but its reply templates omit public contact links.
Email and student ID are not part of those schemas.

Notes:

- Run the API with a single worker. Two polling loops on one token make Telegram return 409.
- `--reload` is fine; the bot restarts with the app.
- A Telegram outage at startup is logged and the API still comes up.

## Authentication

The frontend uses Neon Managed Better Auth. Server-side requests forward a short-lived JWT to the
backend, which verifies it against the configured JWKS URL and maps the auth user ID to `users.id`.
The backend enforces account roles and ownership for order and booking mutations.

## Layout

```
app/
  config.py      settings and URL helpers
  db.py          engine and session dependency
  main.py        FastAPI app (starts the Telegram bot)
  bot/           telegram_bot.py (handlers), queries.py (read-only database access)
  models/        SQLAlchemy models
  notifications/ notification creation helpers
  routers/       listings, cafeterias, services, marketplace requests
  schemas.py     Pydantic response models
  seed/          data.py (the data), runner.py (upserts), __main__.py (CLI)
alembic/         migrations
tests/
```
